# Конструктор инструкций

Локальный MVP на Streamlit для формирования внутренних и внешних инструкций, автоматической предварительной проверки, доработки по замечаниям, ручного согласования и экспорта.

## Запуск

```bash
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt
.venv/Scripts/python -m streamlit run app.py
```

Для предпросмотра через Kimi Work:

```bash
npm run dev -- --host 0.0.0.0 --port 7100
```

## Настройка LLM

Скопируйте `.env.example` в `.env` и самостоятельно заполните:

- `OPENAI_API_KEY` — ключ OpenAI-совместимого API;
- `OPENAI_MODEL` — модель;
- `OPENAI_BASE_URL` — базовый URL, по умолчанию `https://api.openai.com/v1`;
- `OPENAI_TIMEOUT` — необязательный таймаут в секундах, по умолчанию 120.

Ключ не вводится в интерфейсе и не сохраняется в истории. Без настройки API доступны оценка вставленного черновика, сравнение версий, метрики и экспорт. Демонстрационный черновик загружается кнопкой в боковой панели.

## Подключение агентов (выпадающий список в боковой панели)

Список агентов настраивается в файле `agents.json` в корне проекта. Файл локальный (в `.gitignore`), ключи и идентификаторы облака в Git не попадают. Образец — `agents.example.json`.

```bash
cp agents.example.json agents.json
```

Поддержаны два режима вызова (поле `api`, по умолчанию `chat_completions`):

**1. Чистая модель (`chat_completions`).** Полный промпт (системный промпт, правила, шаблон, пример) собирает MVP, модель отвечает текстом. Пример для Yandex AI Studio:

```json
{
  "name": "Qwen3.6-35B — эталон",
  "base_url": "https://ai.api.cloud.yandex.net/v1",
  "api_key_env": "YANDEX_API_KEY",
  "auth_scheme": "Api-Key",
  "model": "gpt://<folder-id>/qwen3.6-35b",
  "extra_headers": {"x-folder-id": "<folder-id>"}
}
```

**2. Облачный агент (`responses`).** Инструкция и поисковый индекс работают в облаке, MVP отправляет только ТЗ. Параметры берутся из сниппета вызова в карточке агента AI Studio:

```json
{
  "name": "Агент — Responses API",
  "base_url": "https://ai.api.cloud.yandex.net/v1",
  "api_key_env": "YANDEX_API_KEY",
  "auth_scheme": "Bearer",
  "api": "responses",
  "extra_headers": {"OpenAI-Project": "<folder-id>"},
  "extra_body": {
    "prompt": {"id": "<id-сохранённого-промпта>"},
    "tools": [
      {"type": "file_search", "vector_store_ids": ["<id-поискового-индекса>"], "max_num_results": 5}
    ]
  }
}
```

Поля: `api_key_env` — имя переменной из `.env` (ключ не хранится в конфиге); `auth_scheme` — `Bearer` или `Api-Key`; `extra_headers`/`extra_body` — дополнительные заголовки и поля запроса. Несколько записей — несколько агентов в списке; сравнение на одном ТЗ ведётся на вкладке «Метрики».

Подводные камни:

- HTTP 401 — смените `auth_scheme` на противоположную схему (`Api-Key` ↔ `Bearer`).
- Ошибка формата модели — попробуйте URI с суффиксом версии, например `gpt://<folder-id>/qwen3.6-35b/latest`.
- HTTP 403 — у сервисного аккаунта нет роли `ai.languageModels.user` на каталог; HTTP 429 — упор в квоту модели.

Навык «Работа с Word» облачному агенту не нужен: DOCX собирается локально экспортером (`exporters.py`) по корпоративному стандарту — A4, поля 1/2 см, Arial 12 pt, заголовки 20/18/16/14 pt чёрные, колонтитул Montserrat 8 pt с копирайтом и номером страницы.

## Сценарий

1. Выберите тип инструкции (внутренняя/внешняя) и вставьте ТЗ в свободной форме; при необходимости прикрепите файлы (Word, текст, картинки макетов).
2. Для внешней инструкции дополнительно загрузите правила и пример внешних инструкций в UTF-8, до 2 МБ каждый.
3. Сформируйте черновик выбранным агентом или вставьте существующий Markdown на второй вкладке.
4. Нажмите «Оценить черновик». При балле ниже 85 или любом критическом замечании рекомендуется доработка.
5. Внесите правки вручную или отправьте замечания в LLM. После доработки проверьте diff и процент изменённых строк.
6. Зафиксируйте вердикт человека, сохраните метрики и выгрузите MD/DOCX.

## Метрики

- Подтверждённость источником — 25%: ссылки и UI-названия в «ёлочках» ищутся во вводных и разрешённой базе, пример не используется как источник фактов.
- Структура — 20%; соответствие списка задач заголовкам — 15%; рисунки — 15%; стиль — 15%; читаемость и полнота — 10%.
- Критические: нарушение NEED_INFO, отсутствие структуры, расхождение задач, несуществующие рисунки, неподтверждённые URL/UI, отсутствие блока уточнений при наличии меток.
- После доработки дополнительно считаются доля изменённых строк и similarity.

Балл — воспроизводимый triage, а не доказательство фактической корректности. Согласование остаётся за человеком. В `data/metrics.jsonl` сохраняются только метаданные оценок, без ТЗ и текста документа.

## Тесты

```bash
.venv/Scripts/python -m pytest -q
```

Тесты используют подменённый транспорт LLM и не обращаются к реальному API.

## Ограничения MVP

- Реальные скриншоты не создаются: сохраняются метки `[СКРИНШОТ: …]` и подписи по правилам.
- Встроенной внешней базы знаний нет, поскольку исходные материалы не были приложены.
- Эвристика проверки императивов, длинных предложений и источников может давать ложные срабатывания; все спорные элементы показываются человеку.
- Цели пилота не являются измеренными результатами: для времени, доли принятия и качества NEED_INFO нужны baseline и размеченная выборка.
